# Macros: extending olang in olang

Part of [the olang book](README.md) · [Language reference](language.md) ·
[Standard library reference](stdlib.md) · [Openness](openness.md)

**Status: experimental.** The design described here is complete and
enforced, but the surface is new and may still be refined; see
[Stability](stability.md#experimental--may-change-or-be-completed).

A `meta fn` is a function that runs while a program is being *loaded*,
not while it runs. It receives the source text of its arguments, returns
source text, and the parser splices that text over the `@` site that
invoked it — before the interpreter, the bytecode tier, or the JIT ever
see the program. Macros are how olang grows without changing: the
language's syntax is frozen, and that is precisely what makes the
program-as-data format a stable contract a macro can rely on.

```olang
meta fn unless(cond, body) = `if !(${cond}) => ${body} else => ()`

let x = 3
@unless(x > 5, println("x is small"))
```

Everything about the system follows from five rules.

## The five laws

**1. Every expansion site says `@`.** A macro is invoked as
`@name(args)` in expression position, or as `@name` stacked above a
`type` declaration. There are no invisible macros: a call without `@` is
an ordinary call, always. You can find every place a program's meaning
is generated by searching it for `@`.

**2. Importing a macro never changes code that doesn't say `@`.** A
macro cannot redefine an operator, intercept an existing call, or
rewrite code outside its own site. The blast radius of any macro is
exactly the set of `@` sites that name it.

**3. The parse is total.** Macro arguments are ordinary olang
expressions, and a file parses completely *before* any macro runs. There
are no token-level or reader macros, and there never will be: the
grammar in `grammar.pest` is the only grammar. A foreign notation (SQL,
a route pattern) rides inside a string literal, where the macro — not
the parser — gives it meaning.

**4. Expansion is pure.** A meta fn runs on a dedicated interpreter in
*meta mode*, where everything effectful refuses with an error: the
modules that reach the outside world or the clock (`fs`, `http`, `db`,
`proc`, `os`, `time`, `random`, `task`, `chan` — including their pure
helpers, since an effectful module should be entirely absent from
expansion), every capability-gated call wherever it lives (the `ods`
file readers and writers), every nondeterministic call the recorder
would have to capture (`dates.now`, `crypto.random_*`), and the parallel
constructs (`spawn`, `par_map`, `par_filter`, `par for`). The
classification is the single table in `src/effects.rs`, shared with the
capability gate and record/replay, so the three can never drift.
Expansion is therefore a deterministic function of the source: the same
file expands to the same program on every machine, every run — which is
what keeps [record/replay](openness.md#open-execution-the-timeline)
exact.

**5. Expansion cannot hide.** `olang expand file.ol` prints the program
the runtime actually receives — every site replaced, every `meta fn`
blanked out with its line numbers preserved. Expansion errors name the
macro and the call-site line.

## Writing a meta fn

A meta fn receives each argument as a `String` holding that argument's
source text, and must return a `String` of source text. Template strings
are the natural way to build it — this is quasiquotation with the same
`${}` the language already has:

```olang
meta fn twice(e) = `(${e}) + (${e})`
println(to_string(@twice(3 * 7)))   // 42
```

Note what `@twice(3 * 7)` expanded to: `(3 * 7) + (3 * 7)` — the
argument's *source*, spliced twice. A macro that evaluates its argument
more than once is a fact the macro author owns; bind it first when that
matters:

```olang
meta fn twice_once(e) = `{ let v = ${e}; v + v }`
println(to_string(@twice_once(3 * 7)))   // 42
```

To *inspect* an argument rather than splice it, parse it: `meta.parse`
returns [the Open AST](stdlib.md#meta--the-program-as-data-the-open-ast)
as ordinary maps, and a macro walks them with the same `map`/`filter`
as any other data. To *compute* with an argument, evaluate it:
`meta.eval` runs source in the same pure sandbox the meta fn itself
occupies. And `meta.lit` renders a value back into source — together
they are compile-time computation in userland:

```olang
meta fn bake(expr) = meta.lit(unwrap(meta.eval(expr)))
let table = @bake(range(0, 6) |> map((n) => n * n))
println(to_string(table))   // [0, 1, 4, 9, 16, 25]
```

The `map` above ran while the program loaded; the runtime received the
literal list. `olang expand` shows exactly that.

A meta fn exists only at expansion time. It is stripped from the program
before evaluation, so calling one without `@` is an undefined-name
error, and nothing about a meta fn's body costs anything at runtime.
Meta fns may call each other as ordinary functions, and a macro's
*output* may contain further `@` sites, which expand on the next round —
bounded by fuel (16 rounds), so a macro that produces itself is an error
naming the loop rather than a hang.

## Decorators: deriving from declarations

`@name` above a `type` declaration passes the declaration's source to
the macro and replaces the declaration with what it returns — usually
the declaration itself plus generated functions. This is the derive
pattern; the macro reads the type's own field list through `meta.parse`:

```olang
meta fn getters(decl) = {
    let t = head(unwrap(meta.parse(decl)))
    let fields = map_get(t, "fields") |> map((f) => map_get(f, "name"))
    let fns = fields |> map((f) => `fn get_${f}(v) = v.${f}`) |> join("\n")
    `${decl}
${fns}`
}

@getters
type Point = struct { x: Int, y: Int }
println(to_string(get_x(Point { x: 7, y: 9 })))   // 7
```

Stacked decorators apply nearest-first: the one directly above the
declaration transforms it, and each one above that receives the previous
result.

For a complete program — `@bake`, `@unless`, `@dbg`, and a `@json`
derive, with tests — see [`examples/macros`](../examples/macros/main.ol).

## Hygiene

Expansion does no invisible renaming. A binding a macro introduces is
visible to the spliced code, and 0.61's block scoping keeps a generated
`let` from leaking past its block — which covers most cases. For a
temporary that must not collide with anything at the call site, ask for
a name no program writes by hand:

```olang no-run
meta fn retry(times, body) = {
    let n = meta.fresh("attempt")
    `{
        let mut ${n} = 0
        loop {
            match ${body} {
                Ok(v) => break Ok(v),
                Err(e) => { if ${n} >= ${times} - 1 => break Err(e); ${n} = ${n} + 1 }
            }
        }
    }`
}
```

## What macros cannot do

The limits are the design, not gaps in it:

- No new syntax, ever. Arguments and output must parse under the one
  frozen grammar.
- No effectful or nondeterministic calls at expansion time (law 4); a
  meta fn that tries gets a refusal naming the module.
- No whole-program view: a macro sees its own arguments and nothing
  else. Program-wide analysis belongs to
  [`olang check --rules`](tooling.md#project-rules), which is the
  read-only half of this system.
- No macro-defined operators, no implicit conversions, no rewriting of
  code outside the `@` site (law 2).
- A meta fn cannot contain an `@` site in its own body — meta fns call
  each other as ordinary functions instead.

Runtime errors are **source-mapped through the expansion**. Every line
of the expanded program carries its origin — untouched source, or the
`@` site that generated it — and a runtime error is translated back
before it is shown. An error in code you wrote points at the line you
wrote, with its exact content, even when a decorator's output shifted
everything below it; an error inside a macro's *output* points at the
`@` site that produced it, names the macro, and offers `olang expand`
to view the generated text:

```text
  × Undefined variable: nope_undefined
 3 │ println(to_string(@boom(x)))
  help: the error is inside code generated by @boom at this site
        (expanded line 3 — run `olang expand main.ol` to see it)
```

The remaining stated limitation: `olang expand`'s printed view is the
expanded text itself, so multi-line expression output shifts the line
numbers of what follows *within that view* (declaration-level output
and meta fn stripping are line-exact). The source map is what keeps
runtime errors immune to that shift.

## Template escapes

A template can contain the three characters that would otherwise be
structural, each escaped with a backslash: `` \` `` is a literal
backtick, `\$` is a literal dollar that will not start an
interpolation, and `\\` is a literal backslash. Every other backslash
pair passes through untouched — `\n` stays two characters, as template
literals have always behaved. The escapes are what let a macro generate
a template that interpolates at *runtime*:

```olang
meta fn logfmt(tag) = `(m) => \`[${tag}] \${m}\``
let log = @logfmt(app)
println(log("started"))   // [app] started
```

## Macro libraries

A top-level `use m` also brings `m`'s top-level meta fns into the
importing file's expansion, which is what makes a macro *library*
possible — [`examples/derives`](../examples/derives/) ships one. The
module is resolved as `m.ol` or `m/index.ol` (dots as directories)
relative to the working directory; a local meta fn of the same name
shadows an imported one, and an imported module's own imports are not
walked. The module file's content is an expansion input exactly like
the source itself.

## Decorating functions and lets

`@name` stacks above `fn` and `let` declarations as well as `type`. A
function decorator receives the declaration source and typically renames
the original (a textual rename of `fn name(` is enough, and
`meta.fresh` supplies the new name) and emits a wrapper under the
original name:

```olang
meta fn noisy(decl) = {
    let node = head(unwrap(meta.parse(decl)))
    let name = map_get(node, "name")
    let impl_name = meta.fresh(name)
    let params = map_get(node, "params") |> join(", ")
    let renamed = str.replace(decl, `fn ${name}(`, `fn ${impl_name}(`)
    renamed + `
fn ${name}(${params}) = ${impl_name}(${params}) * 10`
}

@noisy
fn base(x) = x + 1
println(to_string(base(4)))   // 50
```

Stacked decorators apply nearest-first, so the outermost decorator sees
everything the inner ones generated — which is why a decorator that
generates `test` blocks (like `examples/derives`' `@arbitrary`) goes
outermost: its tests land after every function they call.

## Argument order

Arguments are expanded before the macro runs: by the time a meta fn
receives its argument, the source is macro-free. `@bake(@twice(4))`
hands `bake` the text `((4) * 2)`, never the text `@twice(4)` — the
applicative order function calls follow, to any nesting depth, under
the same fuel that bounds whole-file expansion. The rule exists because
a macro may *inspect* or *evaluate* its argument, not merely splice it;
without the guarantee, `meta.eval` would meet raw `@` text and fail,
while splicing macros would appear to work only because their output is
re-expanded on the next round.

## Real libraries in the corpus

Three macro libraries ship as examples, each imported with `use` by a
real program: [`examples/derives`](../examples/derives/) (serialization,
builders, and generated tests from one type declaration),
[`examples/instrument`](../examples/instrument/) (`@memo`, `@trace`,
`@timed`, `@dbg` — instrumentation as generated code rather than
runtime machinery), and [`examples/contracts`](../examples/contracts/)
(`@require`/`@ensure` contracts that quote their own source, and
`@fmtc`, a format string checked against its arguments before the
program loads). All three run under the example harness and the
tier-agreement corpus.

## In the editor

The language server is expansion-aware. Syntax diagnostics come from
the file as written, so their positions always match the buffer. The
semantic pass — undefined names, unused variables, provable annotation
violations — runs on the *expanded* program, where generated functions
exist (calling one is not an error), and every position is translated
back through the expansion's line map: a problem in your own code lands
on its true line even when a decorator's output shifted the expanded
text, a problem inside generated code lands on the `@` site with its
message prefixed `in code generated by @name:`, and a macro that fails
to expand becomes an error diagnostic anchored at its site.
`use`-imported macro libraries resolve relative to the file's own
directory — in the editor, under `olang check`, and at run time alike.

## In the REPL

A `meta fn` entered in the REPL persists for the session: later inputs
that use `@` are expanded with every previously entered meta fn in
scope. `olang expand file.ol` prints a file's expanded program;
`--diff` shows only the lines expansion changed.

## How this composes with the rest of olang

Generated code is ordinary code. It is type-checked like handwritten
code, promoted to the bytecode tier and the JIT like handwritten code,
capability-gated at runtime like handwritten code — a macro cannot
smuggle an `fs` call past a manifest, because the *runtime* gate judges
the expanded program. Record/replay captures the pre-expansion source
and re-expands deterministically (law 4). And `meta.parse` always shows
source as written, `@` sites and all: the Open AST is the
pre-expansion view, `olang expand` the post-expansion one.
